## 指摘事項

### R5-01（中・設計課題）history のキー集合も違う版差で、段2 と段3 に割れる

再現条件: `history` の `mode` を `evidence_history_fixture_v2` にしたうえで、キーを 1 つ増やす（`extra_key`）か、`decision_at` を落とす。つまり「版が違うのでキー集合も違う」という、版差の典型的な形にする。

期待: `reason_codes` が一意に決まること。

実測: 決まらない。結合案の段2 は「history が辞書で mode キーが存在し、その値が依存 v1 と異なる場合のみ HISTORY_MODE_MISMATCH 単独」と書き、キー集合を条件にしていない。この文言をそのまま実装すると段2 で `HISTORY_MODE_MISMATCH` 単独になる。一方、依存 API を呼んで理由を写像する素直な実装では `inspect_evidence_history` が `INVALID_BUNDLE` を返すため段2 を素通りし、段3 の `INVALID_BUNDLE` 単独になる。どちらも結合案に反していない。

| history | 依存 API | 文言どおりの段2 | 写像する段2 |
|---|---|---|---|
| mode=v2、キー集合は v1 と同じ | `INVALID_MODE` | 発火（段2） | 発火（段2） |
| mode=v2 ＋ 余分キー | `INVALID_BUNDLE` | 発火（段2） | 素通り（段3） |
| mode=v2 ＋ `decision_at` 欠落 | `INVALID_BUNDLE` | 発火（段2） | 素通り（段3） |

影響: 段2 が存在する意味そのものに関わる。履歴 v2 がキー集合を変えない版なら両実装は一致するが、キーを 1 つでも足せば、版差が封筒破損として報告される実装と版差として報告される実装に割れる。R4-01 で「段2 を依存先の分類と一致させた」根拠文は、キー集合が v1 と同じ場合にだけ成り立つ。

重要度: 中（同じ束で出力が変わる。ただし v1 と同じキー集合の版差では一致する）。

推奨する単一の結果: **段2 は依存 API を呼ばずに、`history` が辞書であることと `mode` キーの値だけで判定する**と明記する。キー集合・他キーの妥当性は段2 では見ない。こうすると「束全体を解釈できない版差は、他の診断より先に版差として報告する」という R4-05 の考え方と揃い、キー集合を変える v2 束でも `HISTORY_MODE_MISMATCH` 単独になる。逆の決め方（依存 API の `INVALID_MODE` だけを段2 とする）を採ると、キー集合を変えた版差が段3 へ落ち、段2 がほとんど発火しない段になる。どちらでもよいが、一方に決める必要がある。

### R5-02（低・文書）mode 以外の版差・封筒差の写像先が書かれていない

期待: 9 種のどれになるかが読み取れること。

実測: 書かれていない。`inspect_evidence_history` は `source_origin` 差を `INVALID_ORIGIN` として返すが、結合案にはこの理由の写像先がない。`inspect_strict_input` の `INVALID_MODE` も同様である（参照実装では段3 の `INVALID_BUNDLE` になり、実測でもそう扱うのが唯一の整合的な読みだった）。R4-05 は「結合 mode の版差」と「履歴 mode の版差」の非対称だけを説明しており、依存 3 モードのうち履歴だけが専用理由を持つ理由には触れていない。

重要度: 低（安全側に倒れており誤承認は起きない。ただし実装者が 10 種目を足す誘惑は R4-05 で塞いだ場所の隣に残っている）。

推奨: 「段2 の専用理由は `history.mode` の値差だけに与える。`history.source_origin` 差、`input.mode` / `input.source_origin` 差を含むその他の版差・封筒差は、すべて段3 の `INVALID_BUNDLE` 単独へ写像する」と 1 文足す。

### R5-03（中・設計課題）corrected_after_as_of_count に、過去選択のない必須 subject を数えるかが未定義

再現条件: 必須 subject `events/0001` の初版と訂正版がどちらも `as_of` より後に記録されている束（`lots/0001` は正常）。履歴としては内部整合が取れており、`VERIFIED_OFFLINE_HISTORY` になる。

期待: `corrected_after_as_of_count` が一意に決まること。

実測: 決まらない。結合案の定義は「必須 subject のうち、判定後に初出記録された訂正版（`supersedes` 非 null）が 1 件以上ある subject の数」で、除外規定は「未来の初版だけでは訂正に数えない」だけである。上の束には未来の訂正版が実在するので、文言どおりなら **1**。一方「corrected＝選択した行が後日訂正された件数」と読むと、この subject には `as_of` 時点の選択がないので **0**。参照実装で両方の読みを走らせ、`HISTORY_SELECTION_MISSING` を返しながら片方が 1、もう片方が 0 になることを実測した。

影響: 成功経路では差が出ない（成功には全必須 subject の選択が必要なため）。差が出るのは失敗診断の件数であり、運用者が「当時の証拠が足りなかったのか、後で直ったのか」を読む場面で意味が変わる。

重要度: 中（同じ入力で出力の数値が変わる。ただし成功可否は変わらない）。

推奨する単一の結果: **`as_of` 時点で選択が存在する必須 subject に限って数える**と明記する。名前（判定に使った値が後で訂正された）と一致し、`HISTORY_SELECTION_MISSING` と `corrected>0` が同時に立つ読みにくい状態を避けられる。成功経路の値は変わらない。

### R5-04（低・文書）v1 では二重評価にならないことと、打切り時に部品を呼ばないこと

R4-03 は「選択を `decision_at`、corrected を `as_of` で評価する二重評価」と書いた。一方 R3-03 は成功に時点一致を必須とし、不一致なら段5 でただちに打ち切って `matched=0`・`selection_sha256=null` とする。したがって v1 では、**2 つの時点が食い違ったまま選択を評価する場面が存在しない**。時点一致時は 1 回、不一致時は corrected のために `as_of` で 1 回だけである。文言のままだと、実装者が不一致時にも `decision_at` の選択を計算し、その digest を返してしまう余地が残る（R3-03 は null と決めているので実際には誤りになる）。

同じく、時点不一致で打ち切る場合は `strict_validity` を呼ばないため、R4-06 の遅延 `INPUT_*` 防御には入らない。ここも書いておかないと、部品を先に呼んでから時点を見る実装と、時点を見てから呼ぶ実装で、防御が働く条件が変わる。

推奨: 「二重評価は v2 で時点差を許す場合に備えた設計上の余地であり、v1 では時点一致時の 1 回と、不一致時の `as_of` 1 回しか現れない。時点不一致で打ち切る場合は以降の部品呼び出しを行わない」と 2 文足す。重要度は低い。

### R5-05（低・文書）結合束の 1MiB 上限に、段と CLI の挙動が書かれていない

R2-06/08 は「結合束にも 1MiB 上限を採用する」とだけ書き、どの段で見るのか、超過時に何を返すのかを書いていない。履歴側は F-10 で「検査を開始せず、固定文を stderr、終了コード 2、JSON は stdout に出さない」と決まっている。結合 CLI も同じ規則にするなら、その旨を 1 文書き足すのが安全である。段1 より前（検査開始前）の拒否であり、13 キーの JSON を返す経路ではない、という区別も含めておきたい。
