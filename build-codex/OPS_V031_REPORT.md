## C05：確定したCSVの紐付け

CSVを適用する際に、選択済み通知IDをCSV_FILL.payloadの内部属性 `_applied_proposal_id` へ保存する。再生はこのIDを使い、通知候補を選び直さない。遅着通知の識別情報補完にもこの属性を使う。外部入力に同名属性があっても取り除く。監査のpayload_hashは入力原文側を使い、内部属性追加を再送内容の変更と誤判定しない。

旧CSVイベントに確定IDを遡って書き足す移行はしない。旧規則区間の匿名CSVは当時の記録順で再生され、旧イベントの完全な業務時点再現は別課題。

## 移行CLI

ops/で以下を実行する。

```text
python -m aitrader_ops.migrate --check <台帳コピーのパス>
python -m aitrader_ops.migrate --apply <台帳コピーのパス>
```

checkは入力DBをmode=roで開き、最初の違反のseq/kind/reason、旧規則残高、適用可否をJSONで返す。入力ファイルは更新しない。MigrationErrorはLedgerErrorの派生型で、seq/kind/reason属性と日本語の履歴番号表示を持つ。C14の既存テストは変更していない（英字seqがメッセージにないことだけを調べる旧検証であり、新機能はM01で属性と位置を検証）。

applyも入力は変更せず、SQLite backupで同じフォルダの `<元のstem>.upgraded.sqlite` を作成する。原本と既存出力の上書きをしない。失敗時の作業コピーは診断用に残す。

POLICY_UPGRADE{schema_version:3, at, legacy_last_seq}をコピー末尾へ追記する。マーカーより前の区間はv0.2の互換規則で再生し、以降は現行規則とする。旧最終seqのreplay_knownと旧規則で再生した移行前残高、移行後現在残高を比較する。一致しない場合は移行成功にしない。金融上の不変条件まで無効にする仕組みではなく、旧規則でも破損している履歴はMigrationErrorで停止する。

移行マーカーがあるDBを再度applyしない。新規則で再生可能でも旧規則残高と違う場合は自動移行を拒否する。移行後のDBを実運用先へ差し替える処理はない。今回使ったのはテスト用台帳だけで、ユーザーの原本台帳は移行していない。

旧互換規則は注文中分割・端数切捨て、訂正原価、横断照合、保留解決のv0.2動作を再生するためのもの。過去の欠陥を新イベントで許可するものではない。任意の旧版・未知のスキーマの変換や証券残高との一致は保証しない。

## C12：端株契約

整数にならないSPLITは拒否し、株数・原価を変えない。端株精算の受取金額は `adjust('FRACTIONAL_CASHOUT', amount, code, None, at, note)` で別イベントとして記録する。0以上の整数円、現金を増やすだけで、保有株を切り捨てない。

これは端株処理全体の自動化ではない。拒否された分割を現金精算だけで完了扱いせず、整数株の確定数量・原価調整は証券結果との照合と別途契約が必要。改訂案v1.1へ追記し、仕様本文は未変更。
