# 主系の片側保存復旧：契約の採用提案

2026-09-11、Codexによる設計検討。**未採用・未実装の提案**であり、自動復旧の許可ではない。共通仕様・製品コード・既存台帳は変更していない。[現在の復旧案](RUNNER_RECOVERY_PLAN.md) と [最新の検証結果](README.md) を併読する。

対象は主系journalのINTENTに対して台帳のCREATED/APPROVEDだけが残る中断である。通知キューの模擬SENTを反映する既存 `reconcile_prepared_mock` とは別契約とする。

## 1. 所有runの証明

現状、[runner.py](aitrader/runner.py) はINTENTにownerと候補全体hash、run manifestにinitial_ledger_seqを持つ。一方、[ledger.py](../ops/aitrader_ops/ledger.py) の `create_notice` はproposalと時刻をNOTICE_CREATEDへ記録し、owner run_idを記録しない。候補が同じだけでは、そのINTENTが台帳イベントを作った証明にならない。

**採用推奨：台帳と同一トランザクションで保存する操作受領記録。** 主系はINTENTを保存するとき、変更できないoperation_idを発行する。台帳の専用公開APIへoperation_id、owner run_id、execution_day、候補全体hash、台帳識別子、予期する直前seqを渡す。台帳側はこれらを検証し、NOTICE_CREATEDと受領記録を同じSQLiteトランザクションで保存する。返却するreceiptにはevent_seqとイベント内容hashを含める。journalへのreceipt転記前に中断しても、保存済みoperation_idから台帳側receiptを読み戻せる必要がある。

同operation_id・同入力の再要求は同receiptを返し、再作成しない。同operation_id・異入力、候補IDが既に別操作で存在、想定seqと実seqが違う場合は拒否する。APPROVEDへの変更にも別のoperation_idと元作成receiptの参照を要求し、作成と承認を混同しない。seqの数値だけでなく、台帳識別子と内容hashも照合する。

却下案は「復旧時に同じ候補を見つけたらownerを後付け」「直前seq+1を作成イベントと推測」「journalにだけreceiptを書き足す」の3つ。外部書込との区別ができず、最後の案では台帳書込後・journal書込前の問題が残る。ランダムIDやhashは悪意あるDB同時改ざんの認証ではない。保護されたDB、単一書込運用、操作APIを経由することが前提であり、これを暗号学的な所有証明とは呼ばない。

影響と移行：台帳schemaと公開APIの版を上げ、receiptの一意制約を追加する。既存create_notice利用者を暗黙に所有付きへ変更しない。既存runはreceiptなしのまま読取診断・手動照合対象とし、過去イベントへ所有を推測補完しない。新契約は新規mock runから導入し、ライブ台帳移行は別途扱う。最初はAPI利用者と直接Ledger書込を同時稼働させない。

## 2. 自分の既存予約を二重評価しない公開view

[gate.py](../ops/aitrader_ops/gate.py) は純粋関数で、BUYの余力・予約中銘柄、SELLの予約株数をLedgerViewから読む。[共通仕様](../common/共通仕様_フェーズ2.md) §4の他候補予約・余力制約を維持する必要がある。現在の `Ledger.view()` は全予約を返すため、既に予約済みの自分を通常の新規候補として再評価すると二重計数になり得る。

**採用推奨：検証付きの読取専用 `view_for_existing_notice`（仮称）。** 呼出時に候補IDと所有receiptを照合し、未約定・未発注・未通知のCREATEDまたはAPPROVEDであることを確認する。SENT/UNKNOWN/ORDERED/PARTIAL、訂正・取消等の後続操作がある対象は初版の対象外とし、照合待ちにする。返すviewから対象通知の現存予約だけを除外し、他候補の予約、現金、実保有、簿価、未確認状態は維持する。

BUYはreservedから対象reserveを引きavailableへ同額を戻す。reserved_positionsは対象の寄与だけを除き、同銘柄の別予約があれば残す。SELLは対象のreserved_sharesだけを除く。予約額はProposalから再計算して置き換えず、台帳の現在値を使い、負の残額や不整合は拒否する。損益・DD・評価資産は元の実状態から計算し、予約除外で資産を増やさない。

runnerの日次枠は既存SQLの `pid<>対象` に合わせ、自分を一度だけ扱う。gateへ渡す前に現在の価格・二承認・STOP・未確認・制限を再検証する。viewが返したobserved_seqを実際の状態変更APIにも渡し、別書込でseqが進んだら再取得・再評価が必要である。runner-lockだけでは外部書込を防げないため、台帳側の比較・更新が同一トランザクションでなければ採用しない。

却下案は予約を一度取消して再作成すること、余力にProposal予約額を無条件加算すること、純粋gateに台帳内部属性を参照させること。予約の一時解放、部分約定の無視、責任範囲の混在を招く。通常の新規評価用viewは変更せず、復旧専用APIを追加して移行する。既存通知をこのAPIへ一括適用しない。

## 3. 締切後の履歴修復

主系は07:15以上の候補承認・模擬配信を除外する。既存通知側APIのSENT反映は成功の耐久記録を戻す操作であり、未完了runnerに対する新しい承認とは異なる。

**採用推奨：初版では締切後のINTENT復旧を行わず、予約保持・診断のみ。** 締切前でも現在時刻が元run・受信・receiptイベントより前なら拒否する。現在のSTOP中にNEWを承認可能化しない。STOP情報源の統一は別の前提契約として先に解決する。

後続版で履歴転記が必要になった場合は、承認outboxを作らない独立の監査記録 `HISTORY_RECONCILED`（仮称）を提案する。元承認時刻と修復時刻を別保存し、通知許可falseを持たせ、既存COMPLETED/APPROVEDと混用しない。ただしこの状態の予約保持・翌日照合・終端化と、全通知入口がこの記録を候補として採用しない契約を定めるまでは実装しない。

却下案は「締切後にAPPROVED/outboxを通常形式で復元して送信側に任せる」「元時刻へ巻き戻して復旧する」「未送信と推定して自動解放」。別入口からの配信、監査時刻の偽装、未確認リスクの解放につながる。既存runの時刻や完了状態を書換える移行は行わない。

## 採用前の確認条件

receipt保存前後・台帳反映直後・journal転記前後の中断、同操作再要求と異入力衝突、外部書込でseqが進む競合を試験する。BUY/SELLの別予約・同銘柄予約・部分約定・出金、07:15直前/同時/直後、STOP、非有限/欠損価格を含める。拒否時に予約が減らず、採用時に予約・日次枠・イベントが二重にならないことを確認する。

この3契約だけで運用上の安全性が証明されるわけではない。所有receiptの信頼境界、全書込主体の排他、既存予約除外の算術、STOPの情報源、翌日の保持予約処理が未決なら、読取診断を継続して書込復旧は有効化しない。
