# ops v0.3.3：G07とD08契約5点への対応

2026-09-08、Codex実施。ユーザーの第6回依頼に従いopsを修正。既存テスト、共通仕様本文、主系コードは変更していない。

## G07：採用・実装済み

`_State._on_policy_upgrade` で `rule_version >= 3` をLedgerErrorとして拒否する。移行済み台帳と旧規則区間のない新台帳への内部API経由のマーカー追加は、保存前の試行適用で止まる。正規の履歴再生はマーカーがあると旧規則2から開始するため、初回だけ許可される。`_validate_markers` による1個・直前seq検証は維持した。生SQLの直接書込みを防ぐDBトリガーは追加していない。

任意案のcheck()旧規則失敗の辞書化は**不採用（現契約を維持）**。新規則だけの違反は移行検討用のviolationだが、旧規則も再生不能なら移行元の根拠が得られないためMigrationErrorで停止する。CLIはその例外をseq/kind/reason付きerror JSON・終了コード1へ変換する。G05の既存契約とも整合する。

変更：`ops/aitrader_ops/ledger.py`、`__init__.py`（v0.3.3）、新規 `ops/tests/test_v033_contracts.py`（H01〜H03、3件）。migrate.pyは今回変更していない。

## D08契約5点の採否

| 項目 | 採否と現在の状態 |
|---|---|
| 1. checkの最初の乖離seq出力 | 今回は実装しない。**手作業**と明記。旧新の最終残高しか返さない現APIを維持 |
| 2. 照合済み開始残高への新台帳方式 | **契約案を採用、実装は次回**。新ファイル＋新SNAPSHOTと出所記録。既存台帳のSNAPSHOT置換は禁止 |
| 3. 全量売却後の精算金 | **DIVIDENDを暫定受け皿として採用**。投資由来の現金受取として扱い、構造化noteで精算種別を区別。詳細は下記 |
| 4. 静止・昇格・世代管理 | **手動運用契約を採用**。STOPだけでは不十分。全書込停止・照合・バックアップ・差替え・復旧条件を下記に定義。自動昇格は未実装 |

### 1. 乖離seqを特定する手作業

静止済みの同じイベント列をseq昇順で取り出し、旧規則と新規則で各seqまでの残高（cash、positionsの数量・原価、予約額・予約株数）を順に比較し、最初の相違seqと両側の値を照合記録へ記入する。単に業務時刻で切ったreplay(at)を比較しない。差が後で相殺される場合があるため二分探索ではなく先頭から調べる。途中で片側が再生不能なら「残高乖離」と別に、そのseq・kind・理由を記録する。

現CLIにはこの一覧出力がない。担当者が読取専用でイベントを抽出し、規則別の逐次計算結果と証憑を照合する必要がある。checkのviolation.seqは新規則で拒否された位置であって、旧新残高が最初に違ったseqではない。最終残高が同じことだけで途中の一致を断定しない。

### 2. 照合済み開始残高への移行案（未実装）

別の新台帳ファイルを作り、照合確定済みの現金・保有数量・取得原価・逆指値状態・必要な注文予約から新SNAPSHOTを一度だけ作る方式とする。未解決約定・未報告・CSV保留・遅着報告の対応が残る間は実施しない。単純に未解決項目を捨てて新台帳を作らない。

新SNAPSHOTの公開属性 `provenance` に次を必須とする案：`method="RECONCILED_OPENING"`, `source_path`, `source_sha256`, `source_last_seq`, `reconciliation_id`, `reconciliation_record_path`, `reconciliation_record_sha256`, `actor`, `reconciled_at`（タイムゾーン付き）、`reason`, `cutover_at`, `previous_policy_version`。source_pathとhashは静止・全接続終了・チェックポイント完了後に保全した同じ旧台帳を指す。台帳と照合記録は別媒体にも保存し、pathが移動してもhashとIDで追跡できるようにする。

現在のinit_snapshotにはprovenance引数・必須項目検証がない。今回この方式を実行したわけではない。旧履歴を新台帳へ偽装して複写せず、旧台帳のreplay_knownと新台帳のseqを別の履歴として区別する。旧IDの遅着・再送を新側で二重計上しない照合対応表と遮断手順も次回実装の受入条件とする。

### 3. 保有がなくなった後の精算金

取得済み明細で投資由来の確定受取と確認できた精算金だけ、`adjust('DIVIDEND', amount, code, None, at, note)` を使う。DEPOSITは利用者の外部入金に予約し、精算受取を外部入金として損益から控除しない。ここでのDIVIDENDは台帳上の暫定収納種別であり、税務上の配当分類・実現損益分類を決めるものではない。元本成分と収益成分の内訳は証憑に従って照合記録へ残す。

noteはJSON文字列とし、次のキーを必須とする運用契約：`category="POST_EXIT_SETTLEMENT"`, `settlement_type="FRACTIONAL_CASHOUT"` または `"LIQUIDATION_CASH"`, `code`, `source_event_id`（明細の一意な受取ID）, `source_document_sha256`, `reconciliation_id`, `actor`, `received_at`（タイムゾーン付き）, `reason`。codeは引数と一致、amountは確定した正の整数円、atは実際の受取時刻。架空の担当者・IDを埋めない。手数料等は確認済み明細どおりの別イベントと照合する。

note書式は現在APIが自動検証しない。またadjustは同じ明細IDの再送を自動排除しない。受取IDと既存ADJUSTを人が照合し、二重登録・途中失敗後の盲目的再送を禁止する。不明な金額・出所・数量訂正をDIVIDENDへ逃がさず保留する。数量・原価は変わらず、未保有FRACTIONAL_CASHOUTは引き続き拒否。

主系のnet_external_flowは呼出側から明示入力される。精算金をDEPOSIT扱いでnet_external_flowに加えない運用を必要とし、noteからの自動分類は今回未実装。

### 4. 原本静止・昇格・バックアップの手動手順

この節は将来の運用手順であり、今回実台帳を停止・移行・差替えしていない。

1. 新規候補をSTOPで停止したうえで、スケジューラ、日次処理、返信取込、CSV取込、手動台帳操作を停止し、全Ledger/SQLite接続を閉じる。STOPだけでは返信・照合の書込みが続くため不十分。受信済み・移行中受信イベントは別の耐久キューへ保持し、破棄しない。キュー機能が未実装ならこの運用昇格は保留する。
2. 書込停止後、管理下で必要なWALチェックポイントを完了して全接続を閉じ、その後に原本の最終seq・SHA256・現金・保有・予約を確定する。WALを単に削除したり、本体だけコピーして未反映取引を落とさない。ここでhashを採る前のチェックポイントは準備工程であり、静止基準確定後の原本変更とは区別する。
3. Dropbox外に照合コピーを作り、原本不変を確認する。世代名は `ledger.pre-upgrade.<JST日時秒>.<UUID>.sqlite`、例の日時・UUIDを使い回さず衝突なら中断。原本の退避・照合記録と別ドライブ/NASの世代バックアップを用意する。最低直近3世代と今回の移行元世代を保持し、照合未完了・復旧候補の世代は削除しない。自動削除は今回行わない。
4. 照合コピーをcheck、eligibleかつ照合済みの場合だけapplyする。完成した.upgraded.sqliteの旧最終seq再現、最新残高・予約・保留状態と記録を検証する。旧新差が残るなら昇格中止。原本のseq・hashが静止基準から変わっていた場合も中止し、変更分を把握して新しい基準からやり直す。
5. 全書込停止を保ったまま、運用ファイルを上記の世代名へ退避し、検証済み出力を同じ運用ディレクトリの一意な候補名へコピーしてhashを確認する。接続が閉じていて古い副ファイルも残っていないことを確認し、候補を空いた運用パスへrenameする。既存ファイルを上書きしない。Windowsの二段階差替えは全体では原子的でないので、操作段階と両パスを外部の移行記録に残す。
6. 運用パスの新台帳を再起動し照合完了後、キューの遅着報告をID照合しながら取り込み、未解決なしを確認してから候補生成を再開する。差替え途中の失敗は停止を維持し、旧世代へ戻して再検証する。新台帳に書込みを再開した後は単純に旧世代へ戻さず、追加イベントを保全・照合してから復旧する。

昇格のロック、キュー、バックアップ管理、差替え・復旧の自動化は未実装。現在のmigrate --applyはコピー生成までで、原本の静止や運用昇格を代行しない。

## テスト結果とD08の不安定さ

ops/で指定対象 `python -m pytest ../common/tests/phase2 ../build-codex/tests tests -q` を実行。実際には既存Pythonへ依存探索パスを追加したrunpy起動、`-s -p no:cacheprovider --tb=short` を付加、bytecode無効化。

**最終279 passed in 7.62s。既存276件＋追加3件すべて通過、skip/xfailなし。** 共通162＋主系43＋ops74。

初回は277通過・2失敗（7.99秒）：既存D08の原本hash不一致と新規H03の「補助ファイルも増えない」という誤った前提。H03だけSQLite読取補助ファイル2種を許容し、本体hash不変・他の出力なし・CLI残高一致の検査を維持した。既存テストは一切変更していない。

**残課題：最終全通過でもD08が安定したとはいえない。** D08の_insertは `with sqlite3.connect` でcommitするが、接続をcloseしない。独立診断でcheckの呼出し直前にgc.collectだけを実行すると、台帳本体hashが `09b0078ba899ac722fba03d1fcb52da0fcbb9662002954db17a87fe19745c202` から `5111af6f5a4541bcf9ab14bf8dc0e81292d540f11b7d9ab7045d49d693ad1b9e` へ変化した。checkはまだ実行されていない。この再現は未解放の書込接続終了時のWAL反映と整合し、原本静止前にhashを採るテスト前提の問題を示す。

診断は別の合成一時台帳で実施。gcを無効化して合格させてはいない。Claudeへ、所有するテスト用SQLite接続を明示closeし、その後のhashを基準にする修正と再検証を依頼する。読み取り処理による変更とテスト自身の遅延書込みを混同しない。
