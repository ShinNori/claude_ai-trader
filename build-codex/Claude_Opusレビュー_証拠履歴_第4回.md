## 段3 事前形検査の十分性（依頼の中心。指摘なし）

結合案の段3 の記述どおりに事前形検査を参照実装し、`inspect_strict_validity` の戻り値と突き合わせた。

**構造破損は 16 種すべて段3 で止まった。**`validity_documents` が非 list、要素が非 dict、文書キーが 3 つでない、`id` が空文字・前後空白、`sha256` が非 hex、`sha256` が payload と不一致、payload が非 dict、payload キーが 6 個・4 個、`group` / `code` が非文字列、`record_sha256` が整数・短い、`valid_from` が整数・timezone なし、`valid_until` が解釈不能、ID 重複。

**欠落・不適合は 7 種すべて段3 を通り、段5 で不適合側の理由だけを返した。**証拠 1 件欠落（`VALIDITY_SET_MISMATCH`）、異なる ID で同一 subject が重複（`VALIDITY_SET_MISMATCH` ＋ `VALIDITY_SUBJECT_DUPLICATE`）、`group="prices"` の対象違い、`code` が expected 外、行 hash 差（`VALIDITY_RECORD_MISMATCH`）、`valid_from >= valid_until`（`VALIDITY_PERIOD_INVALID`）、期限切れ（`VALIDITY_EXPIRED`）、開始前（`VALIDITY_NOT_YET_EFFECTIVE`）。

**無作為検査でも漏れは 0 件だった。**期間証拠へ 1〜3 個の無作為な破壊（キーの差し替え・削除・追加、文書の複製・削除・置換、空リスト化、再封印）を加えた束を 4,000 通り生成し、段3 を通った 1,152 通りについて段5 の理由を調べた。構造側の理由（`INVALID_VALIDITY_DOCUMENTS` / `VALIDITY_HASH_MISMATCH`）が現れたのは、**空リストのときの `INVALID_VALIDITY_DOCUMENTS` だけ**であり、これは結合案が明示的に段5 の欠落として扱うと決めた経路である。

理屈のうえでも十分性は説明できる。段3 を通ると、`VALIDITY_SUBJECT_INVALID` の 3 つの発火条件のうち「payload が非 dict / キー集合違い」と「`record_sha256` が非 hex」が消え、残るのは「subject が expected 集合外」だけになる。`VALIDITY_PERIOD_INVALID` も「時刻として解釈できない」が消え、残るのは `valid_from >= valid_until` だけになる。第3回の R3-01 で指摘した「1 つの理由コードが両方の分類にまたがる」問題は、**段3 の形検査によって発火条件の側で切り分けられる**。第3回に私が置いた分類固定試験と合わせて、この構造は今回追加した試験で機械可読に固定した。

三分の首尾一貫も確認した。空リストは段3 を通って段5 で `INVALID_VALIDITY_DOCUMENTS`（欠落）、重複 ID は段3 で拒否（構造）、異なる ID の重複 subject は段3 を通って段5 で `VALIDITY_SUBJECT_DUPLICATE`（不適合）。三者が別経路になることを実測で確かめた。矛盾はない。

## 指摘事項

### R4-01（中・設計課題）段2 の「mode キー欠落 → HISTORY_MODE_MISMATCH」が、依存する履歴 v1 の分類と矛盾する

再現条件: 結合束の `history` から `mode` キーだけを削除する（残り 3 キーは正しい）。

期待: 履歴 v1 の入力契約は「最上位は mode / source_origin / decision_at / entries のみ」なので、キー欠落は構造破損であり、段3 の `INVALID_BUNDLE` 単独になること。

実測: 結合案の段2 は「辞書の mode 欠落/値差は HISTORY_MODE_MISMATCH とする」と書いており、キー欠落を版の問題として報告する。一方、依存先の `inspect_evidence_history` 自身は次のように分類している。

| history の状態 | inspect_evidence_history の理由 |
|---|---|
| `mode` キーを削除 | `INVALID_BUNDLE`（構造） |
| `mode` の値が `evidence_history_fixture_v2` | `INVALID_MODE`（版） |
| `mode` の値が空文字 | `INVALID_MODE`（版） |
| history が非 dict（`[]` / `"x"`） | `INVALID_BUNDLE`（構造） |

つまり v1 自身は「キーの有無＝構造、値の違い＝版」で切っているのに、結合案は欠落を版側へ寄せている。

影響: 封筒が壊れただけの履歴が「版が違う」と報告され、運用者は v1/v2 の取り違えを探す。さらに段2 が `HISTORY_MODE_MISMATCH` と `INVALID_BUNDLE` の 2 種類を出すことになり、「段と理由の対応」が段2 だけ崩れる。

重要度: 中（実装が割れ、診断が誤誘導になる）。

推奨する単一の結果:

- `history` が辞書でない → **段3 の `INVALID_BUNDLE` 単独**（現在は段2 に書かれているが結果は同じなので段3 へ寄せる）。
- `history` が辞書で `mode` キーがない → **段3 の `INVALID_BUNDLE` 単独**。
- `history` が辞書で `mode` キーはあり値が依存 v1 と異なる → **段2 の `HISTORY_MODE_MISMATCH` 単独**。

こうすると段2 は `HISTORY_MODE_MISMATCH` だけを出す段になり、依存先の分類とも一致する。

### R4-02（中・設計課題）時点不一致のときに他の比較理由を併記するかが選択的

再現条件: `input.as_of` を `2026-09-12T06:50:00+09:00`、`history.decision_at` を `2026-09-12T06:51:00+09:00` とし、さらに必須の `events/0001` が履歴に存在しない束を作る。他はすべて正常。

期待: `reason_codes` が一意に決まること。

実測（文書読解）: 決まらない。結合案は「時点不一致時に他の比較理由も検査する**場合は**…」という条件節で書かれているため、`['DECISION_TIME_MISMATCH']` と `['DECISION_TIME_MISMATCH', 'HISTORY_SELECTION_MISSING']` の両方が契約に適合する。段5 は併記可なので、どちらの実装も「規則どおり」と主張できる。

重要度: 中（同じ入力で出力が変わる）。

推奨する単一の結果: **`DECISION_TIME_MISMATCH` 単独**。`required_subject_count` / `extra_subject_count` / `corrected_after_as_of_count` は返し、`matched_subject_count=0`、`selection_sha256=null`。理由は、他の比較理由が「履歴が申告した時点での選択」に対する所見であり、要求時点の所見ではないためで、同じ配列に並べると要求時点の判定として読まれる。段5 の中に「時点一致を先に判定し、不一致ならそこで打ち切る」という内部順序を 1 文で書けば決まる。

### R4-03（低〜中・設計課題）corrected_after_as_of_count を as_of 基準で数える手順が未定義

再現条件: 時点不一致（`as_of` ≠ `decision_at`）の束で `corrected_after_as_of_count` を求める。

期待: 求め方が一意であること。

実測（文書読解）: 「常に `input.as_of` を基準に数え、`history.decision_at` 差で基準を変更しない」と基準は決まったが、**求め方が書かれていない**。内部共用選択モデルは `decision_at` を判定時点として選択を決める設計なので、`as_of` 基準の「判定後に初出記録された訂正版」を得るには、モデルをもう一度 `as_of` で評価するか、版ごとの初出 `recorded_at` を取り出せる形にする必要がある。現状の履歴 v1 の公開出力（`future_revision_count` は全 subject の版数）では代用できないことは、第2回で確認済みである。

重要度: 低〜中（時点一致時は影響なし。不一致時にだけ実装が割れる）。

推奨する単一の結果: 内部共用選択モデルの評価時点を引数にし、**選択は `decision_at`、`corrected_after_as_of_count` は `as_of` で評価する二重評価**と明記する。時点が一致していれば 1 回の評価で足りるので、通常経路の費用は増えない。

### R4-04（低・文書）段5 で観測される INVALID_VALIDITY_DOCUMENTS の写像先が未記載

段3 の形検査を通った後にこの理由が現れるのは、実測のとおり**空リスト（証拠ゼロ件）のときだけ**である。結合案は「空リストは証拠欠落として段5 へ渡す」とは書いているが、**そのとき 9 種のどれになるかを書いていない**。閉じた 9 種に証拠欠落の専用コードはないので `VALIDITY_NOT_SATISFIED` になるはずだが、実装者が新しいコードを足したくなる余地が残る。

推奨: 「段5 で観測される `INVALID_VALIDITY_DOCUMENTS` は空リストのみを意味し、`VALIDITY_NOT_SATISFIED` へ写像する。証拠欠落の専用コードは作らない」と 1 文足す。

### R4-05（低・文書）結合 mode 自体の版差が封筒破損と同じ結果になる

段1 は「最上位 5 キー・mode・source_origin の不一致は `INVALID_BUNDLE` 単独」とする。将来 `history_validity_binding_fixture_v2` の束を v1 API へ渡すと、キーが足りない封筒破損と区別できない。履歴側には `HISTORY_MODE_MISMATCH` があるのに結合側にはない、という非対称が残る。

重要度: 低（安全側に倒れており、誤承認は起きない）。

推奨: 9 種を増やさない方針であれば、「結合 mode の版差は意図的に段1 の `INVALID_BUNDLE` として扱う。履歴 mode と非対称なのは、束全体を解釈できない以上ほかの診断が意味を持たないため」と 1 文で明記し、将来の実装者が 10 種目を足さないようにする。

### R4-06（低・文書）段5 の呼び出し中に INPUT_* を観測した場合の打ち切り

結合案は `INPUT_*` を段3 の条件として列挙している。一方 `strict_validity` は段5 で呼ばれる部品であり、`INPUT_*` はその内部の防御が働いたときに返る。

実際には、段3 で `inspect_strict_input` が合格していれば、`strict_validity` が同じ純関数を同じ入力で呼び直しても合格する（入力不変は既存試験が確認している）ため、**`INPUT_*` は結合経路では到達不能**である。これは設計として健全で、指摘ではない。

推奨: それでも実装の分岐を消すために、「段5 の呼び出し中に `INPUT_*` を観測した場合も、段3 の結果（`INVALID_BUNDLE` 単独・4 件数 0・`selection_sha256=null`）として返す」と 1 文足す。

## 指摘なしと確認した範囲

段3 の事前形検査は必要十分で、段3 が通常の期間不適合を誤って拒否することはない。空リスト・重複 ID・異なる ID の重複 subject の三分は首尾一貫している。`required_subject_count` を検証済み `expected_codes` から独立に算出し `strict_validity.expected_evidence_count` を再利用しないという規定は、第3回 R3-05 の指摘（壊れた `expected_codes` から 4 が算出される）に正しく対応している。段1〜4 で 4 件数すべて 0 と `selection_sha256=null`、診断件数を返せるのは段5 のみ、という区別も明確である。`INPUT_*` をすべて `INVALID_BUNDLE` へ写像する方向に曖昧さはない。

R3-04 は `STRICT_VALIDITY.md` の F-09 節へ反映されており、`INPUT_INVALID_AS_OF` の条件・期待数の扱い（算出前の失敗では 0）・結合側の写像まで書かれている。第3回時点の「どの文書にも記載がない」状態は解消した。

実装コード・既存試験・専用例が今回変更されていないことも、バイト単位で確認した。第1回で私が追加した 54 件と第3回の 11 件は今回も全通過している。
