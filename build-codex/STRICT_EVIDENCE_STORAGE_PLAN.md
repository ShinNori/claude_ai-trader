## 保存する意味を分ける

| 単位 | 保持する情報 | 別の情報として扱うもの |
|---|---|---|
| 原本 | 提供元/契約版、応答本文、原本hashとcanonical hashの区別 | 人工文書hashをHTTP原本の生バイトhashに転用しない |
| 取得記録 | 要求条件、ページの連鎖、観測時刻、記録時刻、取得run識別 | 公表時刻、単元の適用期間、ページ間の同一時点性 |
| 正規化行 | 原本文書と参照先、変換版、元の行hashと正規化値hash | 値の一致だけで同じ出所だったと扱わない |
| 時点の証拠 | sourceの公表時刻、取得による利用可能時刻、適用開始/終了、各根拠 | 予定時刻や基準日を公表完了時刻へ変換しない |
| 訂正 | 新しい版、直前の版/hash、観測時刻、原本 | 古い証拠や過去に生成した判定の上書き |
| 選択記録 | 判定基準時刻、採用した原本/変換/証拠版の集合、結果hash | 最新版の自動再選択や売買承認 |

適用期間が基準時点を含むことと、その証拠を当時知り得たことは別に検査する。strict_validityは前者の人工宣言の整合だけを扱う。後日の訂正を過去の候補に適用するには、当時利用可能だった証拠との区別を保持する必要がある。

## 変更時の規則案

1. 新しい専用ストアだけを対象にする。旧homeや既存市場表を移行・推測補完しない。
2. 同じ取得識別と完全一致する内容の再投入はNO_OP。同じ識別で内容が違う場合は競合として拒否する。
3. 新たな取得で同じ値が観測されても、取得記録は別に残す。値の同一性と取得の同一性を混同しない。
4. 訂正は新しい版として記録し、訂正元の識別/hashを要求する。訂正元不明、循環、同一版の内容変更を拒否する。
5. 検査完了後、原本索引・取得・行参照・訂正参照を同一の保存単位で確定する。途中失敗は未完了として区別し、成功記録を先行作成しない。
6. 保存済み証拠を参照する選択記録を残す。後日の新しい値が、過去の判定原本を暗黙に置き換えない。

## 実装前に確定する点

- 利用する提供元/契約版、取得単位、原本の保存可能範囲と実応答形式。
- 公表・取得・記録・適用日時の正本と時刻境界。現在のAPIで取得できない時刻は未確認として保持する。
- 版と訂正の識別子の出所。内部生成の識別子と提供元の版を区別する。
- 保存期間、原本と索引の同時確定範囲、異常終了後の読取診断。複数DBの原子性・電源断耐久は推測して保証しない。
