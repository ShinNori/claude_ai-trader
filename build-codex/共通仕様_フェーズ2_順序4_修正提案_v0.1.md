```python
def review(*, packet: str, judge: str, transport: str,
           response: dict | None, replay_path: Path | None,

    # {"verdict": models.Verdict, "failure": str | None}
    ...

def build_cli_request(*, judge: str, packet: str, model: str,
                      work_dir: Path, prompt_version: str) -> dict:
    # {"argv": list[str], "stdin": str, "cwd": str | Path,
    #  "shell": False, "network_access": False}
    ...
```

- `packet` は `aitrader.packet.render_packet()` のJSON文字列をそのまま渡す。proposalの14フィールドのhashを再計算する。日付とaware datetimeを復元する。reason/eventsをhash対象に追加しない。全文もログに保存し、同一hashでも参考情報の違いは監査できるようにする。
- `judge` は `claude` / `codex`。入力packet、共通prompt版・内容は両者同一。相手の応答を追加しない。プロンプトは `ops/config/prompts/review-v1.txt`、schemaは同ディレクトリ。promptに数量・価格変更禁止、参照資料の命令は無効、不明情報ならABSTAIN、必須審査観点を含める。新規呼出ごと独立セッションとする。
- transportは `stub` / `cli`。既定の運用設定はstub。明示cli設定と隔離環境の確認がない限り実プロセスを起動しない。build_cli_requestは純粋な計画生成で、ファイル作成・プロセス起動・通信をしない。
- `now` は呼出開始、`received_at` は親が測った完了時刻。stubでは固定時計を注入。naive時刻、完了<開始、未知judge/transport、非正のtimeout、response/replay双方指定はValueError。未信頼JSONの失敗は下表の結果へ畳み込む。
- 締切は `min(proposal.expires_at, expires_atをJSTへ変換した日の07:15)`。同時刻まで可、1µs超過はINVALID。開始時点で超過なら起動しない。完了時にも再確認。08:59の候補有効期限とは別。
- 応答の必須キー: proposal_id、packet_hash、decision、risks、reason、confidence。confidenceはnullまたは有限な0〜1の数値（bool不可）、reasonは200文字以内、risksは空配列または空でない文字列の配列。decisionはAPPROVE/REJECT/ABSTAINの完全一致。
- JSONオブジェクト1個のみ。重複キー、NaN/Infinity、コード枠、前後の説明、必須欠損、未知キーを拒否する（additionalProperties=false）。数量・価格・銘柄を含む余分なキーは値が同じでも拒否する。未知キー内へ提案を埋め込む応答もINVALID。自然言語reason内の意味解析を安全性の根拠にはしない。
- `judge/model/cli_version/run_id/received_at` は親が指定し、AI自己申告を採用しない。Verdictはこの親メタデータと対象ID/hashを使う。対象不一致の生値は監査記録へ残す。

| 状態 | failure | Verdict.decision |
|---|---|---|
| 正常 | null | 応答のdecision |
| 時間切れ、elapsed_seconds > timeout_seconds | timeout | ABSTAIN |
| exit_code != 0 / Claude error envelope / 利用上限等 | process_error | ABSTAIN |
| JSON/型/スキーマ/最終応答欠損/数量等の追加 | malformed | INVALID |
| 入力hash再計算不一致・応答ID/hash不一致 | hash_mismatch | INVALID |
| 開始または完了が締切超過 | deadline | INVALID |

複数該当時の優先順位は入力hash→締切→timeout→process_error→malformed→応答ID/hash。INVALIDは共通仕様のゲートで不許可になる。純粋な審査ABSTAINにはfailureを付けない。

### 2.1 stubの記録とCLI応答の抽出

`response`、またはreplay_pathのUTF-8 JSONファイルは同一形式:

```json
{"stdout":"...", "final_message":null, "exit_code":0, "elapsed_seconds":1}
```

ClaudeはstdoutのJSON外包 `type=result, subtype=success, is_error=false` を検査し、その `result` **文字列**をさらにJSON解析する。本案は `--json-schema` を使わないためstructured_outputとの暗黙フォールバックはしない。CodexはstdoutのイベントJSONLを判定として扱わず、`final_message`（最終応答ファイルを親が読み取った文字列）を解析する。最終応答なしでstdoutにAPPROVEがあっても無効。recordの余計なmetadataを親のモデル名等へ転記しない。

各試行をlog_dir以下のUTF-8 JSONLへ追記。最低限: packet（入力文字列）、record（上記4項目）、judge、model、cli_version、run_id、prompt_version、開始/完了時刻、failure、正規化verdict。stdout/stderrはサイズ制限・秘密値マスクを行い、LINE秘密、認証ヘッダ、環境全体は記録しない。ログ保存失敗は承認を外へ返さず例外で停止する。既存runnerの決定ログにはこのfailureを関連付ける。replayは記録だけを使い、実CLIへフォールバックしない。

### 2.2 CLI計画と隔離（実接続の合格を意味しない）

基本argv（shellを経由せず配列で渡す。入力は共通stdin）:

```text
claude -p --output-format json --max-turns 1 --tools "" --strict-mcp-config --mcp-config <empty-mcp.json> --model <configured-model>
codex exec - --output-schema <schema.json> --output-last-message <unique-out.json> --sandbox read-only --skip-git-repo-check --model <configured-model>
```

Claudeの `--tools ""` は配列の空文字1要素を保持する。`--allowedTools`はツール禁止の代替にならない。空MCP設定は `{"mcpServers":{}}`。ユーザー/プロジェクトのhooks、plugins、skills、MCP、履歴をロードしない独立環境を準備し、管理設定で外部MCPが強制される等、隔離を証明できない環境は起動拒否。隔離ホームと読取可能ファイルをOS境界で制限する。read-onlyだけでは秘密ファイルの読取防止にならない。

ネットワーク不使用は**審査ツールによる検索・任意通信の禁止**。ホスト型モデルの推論通信そのものは不可避なので、全面ネットワーク遮断した環境ではcli審査は動かない。将来の実接続では親の推論通信のみ許す配置が必要。本ループではその例外を有効にしない。`network_access=False`という計画フィールドやCLIフラグだけをOS隔離の証拠にはしない。

親は120秒上限と残り締切時間の短い方で監視し、超過時は子孫プロセスを停止・回収する。Windowsは非表示で起動。個別作業ディレクトリ、固有最終出力パス（古いファイルを再利用しない）、モデル明示、許可リスト式環境変数、MCP/拡張なしを前提にする。Codexの--jsonは監査イベント用であって判定JSONの指定ではない。両CLIの実際の版/help/隔離の実測は後続の実接続工程で記録する。現時点では公式資料の確認のみ。

`settings` は `broker.link_template`、`line.allowed_user_id`、`line.monthly_budget`（既定200）を持つ辞書。秘密は含めない。未設定の実送受信設定をstubから補完して本番送信しない。transportはstub/line、stubの送信結果列は `success/failure/timeout`（成功、明確な不受理、成否不明）。列が尽きたら勝手に成功とせずfailure。lineは本ループでは呼ばない。

### 3.1 文面とリンク

| kind | 内容 | 二重承認 | STOP |
|---|---|---|---|
| NEW | 現物BUYの新規候補 | 必須 | 停止 |
| EXIT | 保有現物SELLの手仕舞い | 必須 | 継続 |
| RECONCILE | 照合・障害・日次状態 | 不要 | 継続 |
| RISK | 固定ルールのリスク警告 | 不要 | 継続 |

NEW/EXITはLINE Flex `type=flex, altText, contents.type=bubble` の1候補1枚。proposal、両Verdict、contextから、候補ID・銘柄コードと名前・現物/売買方向・株数・寄付指値・有効期限・戦略と版・双方の判断/理由・リスク・本日件数/上限（初期2）・口座確認時刻・予約後余力・楽天で余力/保有/未約定確認・7:40以降発注の案内を表示。confidenceとその数値は全フィールドから除外。altTextにも漏らさない。価格/余力は桁区切り、時刻はJST。

contextの候補用キー: name、new_sent_today、max_new_per_day、account_confirmed_at（aware datetime）、available_after。RECONCILE/RISKはtextまたはstatusを使う。statusと必須文言は `NO_SIGNAL=本日サインなし / REVIEW_INCOMPLETE=審査未完了 / REJECTED=候補はあるが不承認 / DATA_MISSING=データ不足 / ERROR=障害`。NO_SIGNALは日付単位のキーで1日1通。審査不能をNO_SIGNALへ変換しない。

URLは設定テンプレートの `{code}` のみを展開。HTTPSで、ホストは `rakuten-sec.co.jp` またはその正規サブドメイン（区切りの`.`を確認）、userinfoなし。member.rakuten-sec.co.jp・セッション情報を含む会員URLは禁止。未定義置換・外部URL・スキーム違反はValueError。コードは既存4〜5文字英数字契約で検証。文字列部分一致で偽ドメインを許可しない。テンプレート未設定の候補カードはエラーとし、勝手に候補1を選ばない。

ボタンのpostback.dataはJSON文字列 `{"action":"ORDERED", "proposal_id":"..."}` 等。ラベル写像: 発注した→ORDERED、一部約定→PARTIAL、全部約定→FILLED、取消した→CANCELLED、見送り→SKIPPED。売買/数量/価格はボタンに埋めて実約定とみなさない。

### 3.2 outbox、送信成否、予算

- enqueueは外部送信しない。戻り値は `{key, state, duplicate}`。key非空、未知kind、不明候補、候補のAPPROVED/SENT以外の状態、同一keyの異なる内容はValueError。同一内容の再登録はduplicate=true。NEW/EXITのproposal_id必須。呼出側は既存gateを通しAPPROVEDを台帳へ記録した候補だけをenqueueする。notifyはAPPROVEDを自作しない。
- kind、proposal_id、本文、受信者、retry_key、状態、試行履歴をSQLiteへ永続化。同一候補はキーを変えても重複候補カードを出さない。状態観測は `flush` と `status` の公開結果で行い、試験は内部SQLへ依存しない。
- flushは挿入順、1回につき対象行を各1回処理し、試行/抑止した行の `{key,state,retry_key}` を返す。既にSENTの行は対象外で空リスト。候補の期限・07:15・STOP・台帳状態を送信直前に再確認する。
- 成功確認後のみoutbox SENTと台帳 `notice_state=SENT`。順序は予約→enqueue→送信→成功確認→SENT。失敗時に予約を解放しない。PENDING（未送信/明確な失敗）、UNKNOWN（成否不明）、SENT、EXPIRED、STOPPED、BUDGET_BLOCKEDを区別する。
- 送信中に落ちた場合も同一retry_key・同一受信者/本文で再試行。LINEは `X-Line-Retry-Key` にUUIDを使い、初回から固定。409も正規の同一要求受理済み応答と確認できた場合だけ成功として整合させる。単なる競合は成功にしない。再試行有効期間（公式は24時間）を超えたUNKNOWNは新キーを作らず照合待ち・ローカル警告。送信受付成功は既読や本人への到達の保証ではない。
- DBの排他・一意制約と送信中claimで並行flushの二重送信を抑止する。outboxとledgerの確定が別DBの場合、成功を耐久記録した上で同一成功からledger状態を再適用して復旧できる手順が必要。ネットワーク送信とSQLiteの完全な単一トランザクションを主張しない。
- 07:15超過またはexpires_at超過の候補待ちはEXPIREDで送らない。UNKNOWNは「未送信」と断定せず照合警告。STOP中のNEWはSTOPPEDで送らず、EXIT/RECONCILE/RISKと受信は継続。解除後も期限を再評価する。
- 月予算はJST暦月、許可本人1人への1通知を1通として全kind合算、上限200。外部送信前に枠を原子的に確保。明確な失敗は枠を戻す、UNKNOWNは枠を保持、同一retryの成功は二重加算しない。他経路から公式アカウントで配信した消費分は本番導入時に照合する。
- 超過は全kindをBUDGET_BLOCKEDとし課金枠へ自動拡張しない。ローカル状態にBUDGET_EXCEEDEDを残す。警告のために201通目を送らない。新月は新しい予算、古い候補/日次通知を自動一括配信しない。未解決リスク/障害は新しい評価結果で再登録する。
- status戻り値: `{monthly_used: int, stopped: bool, alerts: list[str]}`（追加キー可）。monthly_usedは成功と成否不明予約を含む。テストの成功200件では200。local alertsはLINE障害/予算超過/再試行期限を確認できる。別経路通知の自動送信はユーザーによる選定後。

## 4. Webhook処理

HTTP受け口から生body bytesとX-Line-Signatureを渡す。HMAC-SHA256(channel secret, **未加工body**)をbase64化し、constant-time比較。JSON整形・解析・userId検査・DB記録より先に署名を検証する。失敗は `{http_status:401, results:[]}`、署名正常で壊れたJSONなら400。空eventsは `{http_status:200, results:[]}`。正常リクエストはイベントごとの結果を返しHTTP200、処理中の永続化障害は5xxで再送可能にする。

各イベントは許可userIdかつsource.type=userの1対1トークに限定する。group/room/不明sourceはFORBIDDEN。署名正常は利用者認証の代わりにならない。webhookEventId必須。同ID/同業務payloadはDUPLICATE、同ID/異なるpayloadはCONFLICT。再配信のdeliveryContext.isRedelivery等の配送メタデータ差は同一業務payloadとして扱う。受信者・イベント型・timestamp・postback内容の差は競合。

postback.dataのactionを§3.1の写像で `Ledger.report(TradeEvent(...))` へ接続する。event_idは `line:` + webhookEventId、source=line、proposal_idは一致する既存候補。qty/price/fee、broker_order_id、約定時刻は実報告値を使い、候補の指値や予定数から推測しない。コード・方向・口座は台帳候補から取得し、自由入力の差し替えは禁止。

PARTIAL/FILLEDは `qty`（今回分の増分株数）、`price`、`fee`が必須。省略時はNEEDS_DETAILSで残高を変更せず、確認入力へ誘導する。部分約定の後のFILLEDも残り今回分だけ（累計100で再加算しない）。時刻はpayload `at`（aware ISO、実約定時刻）があればその値、なければLINE event.timestampを本人の報告時刻として記録する。後日訂正可能な記録とし、約定時刻そのものと断定しない。未来時刻はINVALID。ORDERED/CANCELLED/SKIPPEDの金銭値省略は0として、既存reportの状態遷移へ委譲する。

戻り値 `results` は受信順の `{"event_id": webhookEventId, "status": ...}`、必要ならreport結果・確認内容を追加。状態:

| status | 意味 |
|---|---|
| APPLIED | report.appliedで受理 |
| IGNORED | 遅着ORDERED等の既存reportのignored |
| PENDING | 台帳の既存cutover等の保留 |
| DUPLICATE / CONFLICT | 同ID再送 / 同ID改変 |
| NEEDS_DETAILS | 実約定入力不足。残高不変 |
| UNKNOWN_PROPOSAL | 不明候補。残高不変 |
| INVALID | 欠損/型不正/未来日時/不明action/台帳入力拒否 |
| FORBIDDEN | 許可本人以外、group/room |
| STOPPED / RESUMED / RECONCILIATION_REQUIRED | 停止再開操作 |

通知期限後でも実約定・取消・発注報告を受け付ける。期限切れを見送りとみなさない。順序逆転は台帳の既存規則を使い、FILLEDの後に届いたORDEREDでUNCONFIRMED/ORDEREDへ戻さない。イベント日時だけを使って未処理の部分約定を捨てない。報告内容の確認文面を返し、不足入力は元eventを改変せず新eventで送る。訂正は既存CORRECTION契約の対象ID明示・人間の確認手順を使う（今回の5ボタンに自動訂正は追加しない）。

重複台帳は永続化。report適用後に受信管理保存前で落ちても、固定 `line:eventId` によるreport冪等性で再処理し、残高二重計上を防ぐ。NEEDS_DETAILS等もそのeventの処理結果を記録する。並列同ID処理は排他する。

STOP/RESUMEは署名・userId・1対1認証をすべて通したtext message（完全一致）またはpostback actionのみ。停止状態を永続化し、STOPファイルがあればOR条件で新規停止。RESUMEは人間の認証操作に加え、親が確認した `reconciled_at >= 最新STOP時刻` かつ `reconciled_at <= now` が必要。Webhook本文のreconciled_at自己申告は使わない。未確認注文/照合保留/他の固定リスク停止は既存gateで独立して評価し、RESUMEで解除しない。STOPファイルが残る場合は実効停止を保持する。遅着STOP/RESUMEで新しい操作を巻き戻さず、操作時刻と記録を監査する。

## 5. 先行テストと後続検証

`common/tests/phase2/test_judges.py` / `test_notify.py` は各テスト内で新モジュールをimportし、未実装のImportErrorを個々の失敗として計測する。skip/xfailなし。Popenとsocket.connect/create_connectionを禁止し、stubの合成入力のみ。既存487件には変更を加えない。各ケースは公開APIを使う。

今回の先行テストが通ってもOS隔離、実CLIの互換性、実LINE配信・HTTP受け口・並行クラッシュ耐性を全て実証したことにはならない。Claude実装時に追加する独立試験: タイムアウト子孫回収の模擬プロセス、出力サイズ上限、ログ書込失敗、並行flush/並行webhook、成功記録と台帳更新間のクラッシュ復旧、UNKNOWNの予算予約とretry期限、STOPファイル連携。受入テストは緩めず不足点を独立試験で補う。
