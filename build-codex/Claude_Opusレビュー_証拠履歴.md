### 実装上、特に妥当と判断した点

版の同一性を `subject`・payload hash・訂正元の 3 点で決めているため、同じ `revision_id` の内容がすり替わる経路と、別 subject が同じ `revision_id` を名乗る経路の両方が `REVISION_CONFLICT` で閉じる。訂正の親が常に「現在の末尾」に固定されるため、版識別子は履歴内で一意になり、巻き戻し・分岐・循環が構造的に発生しない。完全再投入の判定を時刻逆行の検査より前に置いている順序も意図どおりで、古い受取の再投入が誤って改竄扱いにならない。

履歴 payload の canonical 表現は `strict_input` の lots/events 行と同一であり、`{"code":"0001","lot_size":100}` の SHA-256 が両者で一致することを実測した。結合案の項目 3・4 が要求する hash 突合は、表現変換なしにそのまま成立する。

## 指摘事項

重要度は、実データ接続前に決めないと後戻りが大きいものを「中」、文書・堅牢性の改善を「低」とした。**いずれも現行コードの誤動作ではない。**

### F-01（中・契約の欠落）銘柄コードと識別子の正規形が固定されていない

再現入力: `subject.code` を `０００１`（全角）、`00 01`（内部空白）、`00\n01`（改行入り）、`0001​`（ゼロ幅空白付き）にした履歴。payload の `code` も同じ値にする。

期待結果: 銘柄コードの形式違反として拒否、または少なくとも正規化して同一視。

実際の結果: 4 通りすべて `VERIFIED_OFFLINE_HISTORY`。それぞれ別 subject として独立に選択される。`_trimmed` は「空でない・前後に空白がない」しか要求していない。`strict_input` の `expected_codes` も同じ強さで、両者に共通の形式規則がない。

影響: 単体では fail-closed であり、直ちに誤承認は起きない。問題は結合後で、結合案 項目 2 は必須 subject を `expected_codes × {lots, events}` のバイト一致で突き合わせる。見た目が同一で一致しない入力は「証拠欠落」として現れ、原因の特定が難しい。将来どちらか片側にだけ正規化を入れると、逆に誤一致へ倒れる。

修正案: `STRICT_INPUT.md` と `EVIDENCE_HISTORY_FIXTURE.md` に共通の銘柄コード規則（例: Unicode NFC 済みで `^[0-9A-Z]{4,5}$`、制御文字と空白を一切許さない）を書き、`_trimmed` とは別の検査関数を両モジュールで共用する。識別子（`receipt_id`・`revision_id`）にも制御文字の禁止と長さ上限を与える。

### F-02（中・契約の欠落）`selection_sha256` だけでは結合を外部検証できない

再現入力: `examples/strict_input_valid.json` と `examples/evidence_history_valid.json`。

内容: 呼び出し側は `strict_input` が参照する lots/events 行の canonical hash を再計算できるが、`selection_sha256` は `{group, code, revision_id, sha256}` の配列に対する hash であり、`revision_id` は `strict_input` にはどこにも存在しない。したがって**現在の公開出力だけでは、外側で digest を再計算して突き合わせることが原理的にできない**。

結合案は「履歴 API は現在 digest のみ返すため、外側で履歴選択を再実装しない」と書いており方向は正しいが、**その結論として何を採るかが決まっていない**。

修正案: 結合は「検証済み選択モデルを内部で共用する単一 API」に固定すると明記する。どうしても外部照合を残すなら、版識別を落とした `selection_value_sha256`（`{group, code, sha256}` のみ）を追加で公開する。`revision_id` 入りの digest は「同値の別 revision を区別する」用途で維持する。公開 API へ原本本文を足す必要はない。

### F-03（中・仕様上の限界）再投入判定がバイト一致のみで、等価な時刻表記差を改竄と同じ理由にする

再現入力: 正常履歴の先頭 entry を複製し、`receipt_id` を変えずに `observed_at`・`recorded_at` だけを `2026-09-12T05:00:00+09:00` → `2026-09-11T20:00:00+00:00` のように**同一時点の別表記**へ書き換えて追加する。

期待結果（契約どおり）: 正規化 JSON が違うので拒否。

実際の結果: `RECEIPT_CONFLICT`。すなわち**実装は契約どおり**で、これはバグではない。

論点: 同じプロジェクト内で時刻の同一性判定が 2 通りある。`STRICT_VALIDITY.md` は「異なる timezone 表記でも同一時点として比較する」と明記し、履歴の判定時点比較も aware datetime の比較なので UTC 表記でも通る。一方、再投入判定だけがバイト一致である。実取込で提供元の直列化やタイムゾーン表記が変わると、無害な再取得が改竄シグナルとして上がる。

修正案: `STRICT_EVIDENCE_STORAGE_PLAN.md` にどちらを採るか明記する。案 A は「時刻フィールドは比較前に単一表現（UTC・マイクロ秒）へ正規化してから完全一致を判定する」。案 B は現行を維持しつつ、時刻表記だけが異なる場合を `RECEIPT_REPRESENTATION_DIFF` として改竄と別の理由コードに分ける。実接続前にどちらかへ固定する。

### F-04（低〜中・仕様上の限界）`recorded_at` の単調性が入力全体への要求で、source 別バッチを受け付けない

再現入力: lots の 2 件（06:00、06:10）の後ろに events の 1 件（05:30）を置いた履歴。3 件とも単体では正常で、subject ごとに見れば矛盾はない。

期待結果: 契約どおりなら拒否（「新しい receipt は入力順に `recorded_at` が逆行しない」）。

実際の結果: `RECORDED_AT_REVERSED`。同じ 3 件を `recorded_at` 昇順へ並べ替えると成功する。**実装は契約どおり**。

影響: 実取込では endpoint・source ごとにバッチが届くため、投入前に全 receipt を跨いだ merge-sort が必要になる。この義務が保存契約に書かれていない。

修正案: 保存契約に「投入前に全 receipt を `recorded_at` 昇順へ整列する」責務を明記する。または単調性の要求を subject 単位へ緩め、全体順序は保存層の責務と切り分ける。どちらを採るかを契約と試験で固定する。

### F-05（低〜中・仕様上の限界）成功と「必要証拠の充足」を取り違える余地

再現入力: 正常履歴に対し `decision_at` を全 entry の `recorded_at` より前に置く。

実際の結果: `VERIFIED_OFFLINE_HISTORY`、`selected_revision_count=0`、`future_revision_count=3`、`selection_sha256` は空配列の hash `4f53cda18c2baa0c0354bb5f9a3ecbe5ed12ab4d8e11ba873c2f11161202b945`（固定値）。

`EVIDENCE_HISTORY_FIXTURE.md` はこの限界を明記しているので**文書の欠落ではない**。問題は、成功時の出力だけを見る呼び出し側に「選択 0 でも成功しうる」ことを示す否定的な標識がなく、空配列の digest が正規の digest と同じ形で返る点である。

修正案: 結合 API に `required_subject_count` と `matched_subject_count` を必須出力として持たせ、履歴単体 API はこのままとする（単体に真偽フラグを増やすと、結合前に充足を語れるかのような誤解を招く）。契約側には「`selection_sha256` を充足の代用にしない」だけでなく「空配列 digest の固定値を期待値に焼き込まない」と一文を足す。

### F-06（低〜中・契約の欠落）適用期間証拠自身の取得時刻が未収録であることを、結合結果に残す規定がない

結合案の本文は「適用期間証拠そのものの観測・記録時点は現履歴モデルに含まれていない」「両者を結ぶ追加の人工証拠契約なしには『当時すべて分かっていた』と認定しない」と正しく書いている。しかし、結合の**要求一致 1〜5 と必要な反証のどちらにも、その未証明を出力へ残す規定がない**。結合が成功したとき、呼び出し側は「当時の入力適格性が確認できた」と読みうる。

修正案: 結合結果に固定の注記種別（例 `PERIOD_EVIDENCE_NOT_TIMED`）を成功時にも必ず含める、または `period_evidence_timed=false` を必須出力にすると契約へ書く。期間証拠へ `observed_at`・`recorded_at` を与えて履歴 subject 化するのは、その次の工程として分けて設計する。

### F-07（低・契約の未決）余分な subject の扱いが未決のまま

結合案は「余分な subject を拒否するか無視するか」を未決として残している。無視を選ぶと、無関係な subject を大量に含む履歴でも結合が通り、監査時に「何を見て決めたか」が絞れない。

修正案: 結合層では余分 subject を**拒否**し、`extra_subject_count` を返す。履歴単体モデルは現状どおり（必須集合を持たない）を維持する。

### F-08（低・同梱例）同梱の 2 例は結合の前提を満たさない

`examples/strict_input_valid.json` の `as_of` は `2026-09-12T06:50:00+09:00`、`examples/evidence_history_valid.json` の `decision_at` は `2026-09-11T07:00:00+09:00` で、結合案 項目 1（timezone 込みの同一時点）を満たさない。さらに履歴例は lots の 1 subject だけで events を持たないため、項目 2 の必須 subject（`expected_codes × {lots, events}`）にも欠ける。

現在は両者が独立した検査なので**不具合ではない**。結合の実装時に、同一時点で lots と events の両方を持つ結合専用の例を新規作成する必要がある。既存 2 例は単体用として維持する。

なお、結合が必要な理由は同梱例だけで再現できる。`evidence_history_valid.json` の `decision_at` を `strict_input` と同じ `2026-09-12T06:50:00+09:00` に合わせると、履歴は訂正後の `lot_size=200`（版 `artificial-v2`）を選び、`strict_input` は `lot_size=100` を参照したまま、**双方とも単体では VERIFIED を返す**。両者が別の値を見ていることは現状のどの検査でも検出されない。結合案の動機づけとして、この 1 例を文書へ載せる価値がある。

### F-09（低・堅牢性）到達不能な防御分岐と、他モジュールの不変条件への依存

`evidence_history_fixture.py` では、entry 全体の canonical 化が成功した後に評価される `payload_hash is None`、`_canonical(supersedes)` の例外捕捉、`selection_hash is None` の 3 箇所が到達不能である（部分構造の直列化は全体が直列化できれば必ず成功する）。害はないが、読み手には「ここで失敗しうる」と誤読される。

`strict_validity.py` の選択行解決（`_resolve` の呼び出し）は try/except を持たず、「`inspect_strict_input` が VERIFIED を返したなら全参照が解決可能」という**他モジュールの不変条件**に依存している。現状は安全だが、`strict_input` 側の検査順や早期復帰を変えると例外が外へ漏れる。

修正案: 到達不能分岐には意図をコメントで残す。`_resolve` は防御的に囲み、失敗時は固定理由（例 `INPUT_SOURCE_REFERENCE_INVALID`）へ落とす。

### F-10（低・文書）CLI の入力上限が履歴契約に書かれていない

CLI が使う限定 JSON 読取は 1 MiB の上限を持ち、超過・シンボリックリンク・読取中の差し替え・重複キーを拒否する（重複キー拒否は canonical hash の一意性に効いており妥当）。履歴は件数に比例して大きくなるため、上限と超過時の挙動（固定文・終了コード 2）を `EVIDENCE_HISTORY_FIXTURE.md` に明記すべきである。

## 結合案への修正提案（まとめ）

結合案そのものの方向は妥当で、要求一致 1〜5 と必要な反証 6 件は、私が独立に洗い出した論点をほぼ覆っている。次の実装前に、以下を契約へ書き足すことを提案する。

1. 銘柄コードと識別子の正規形を両モジュール共通で固定する（F-01）。
2. 結合は内部の共用選択モデルで行うと明記し、外部照合を残す場合のみ `selection_value_sha256` を追加する（F-02）。
3. 時刻フィールドの同一性判定を「正規化後の一致」か「表記差を別理由に分ける」かへ固定する（F-03）。
4. `recorded_at` 昇順整列の責務が投入側にあることを明記する（F-04）。
5. 結合出力に `required_subject_count` / `matched_subject_count` / `extra_subject_count` を必須とする（F-05、F-07）。
6. 期間証拠が時刻を持たないことを、成功時にも出力へ残す（F-06）。
7. 必須 subject に「判定後の訂正が存在する」場合の件数（例 `corrected_after_as_of_count`）を返す。値は出さない。過去選択を使う限り結果は正しいが、先読みの危険が近いことを運用者が見えるようにする意味がある。
8. 結合専用の同梱例を新規作成する（F-08）。

## 追加した試験

`build-codex/tests/test_evidence_history_opus_review.py`（54 件、0.19 秒、全通過）を新規追加した。既存試験の期待値は変更していない。モジュール内部の helper を使わず、公開契約から canonical 化と hash を独立に再実装しているため、内部表現の変更が試験を素通りできない。

固定した性質は、後日の訂正が過去の判定を変えないこと（明示 1 件＋無作為 40 seed）、判定時点の境界（同時刻は選択・1 マイクロ秒前は未来）、判定時点の timezone 非依存、同一時点の別 subject の順序非依存、同値訂正でも版識別が digest に残ること、既知版が別の親を名乗れないこと、2 つ目の根・別 subject の head 継承・既存 subject から他 subject head への参照がいずれも拒否されること、時計だけを変えた再投入が競合になること、失敗時に理由 1 件・件数 0・digest なしであること、全版が未来でも成功し空配列 digest を返すこと（限界の明示的な固定）、履歴 payload と `strict_input` 行の canonical 表現が一致することである。

入力順の全体単調性（F-04）も、契約どおりの挙動として 1 件固定した。仕様を変える場合はこの試験が落ちるので、変更が意図的だと分かる。

## やっていないこと・残る限界

全体一括実測（2515 件）は環境を用意していないため未実施で、Codex の報告値を検証していない。Windows 実機・PowerShell 経路・実際の Codex ランタイム Python では実行していない。永続化、排他、電源断耐久、原本署名、実公表時刻、実適用期間、全銘柄の網羅性、提供元の真正性はいずれも本レビューの対象外で、依然として未保証である。

人工入力に対する内部整合の検査が正しいことは、その入力が実際の市場で起きたことを意味しない。今回の結論を実売買適格性へ昇格させないこと。
