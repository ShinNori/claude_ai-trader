# ops v0.2 再々レビュー（2026-09-08）

前提146件は通過を維持。新しい `common/tests/phase2/test_ops_rereview2.py` は16関数・16ケースで **5通過・11失敗**。opsコードと既存テストは変更していない。各失敗の分類はREADME末尾。以下は `ops/Claude対応結果.md` 第2回の5項目への回答。

## 1. 不変条件：数値が非負でも原価と注文の意味は壊れる

S01のEXTERNAL買注文取消、S02の未注文株の分割は通過。一方S04では、200株を単価1,000円で保有→100株売却→100株を2,000円で買付→最初の売却価格を訂正すると、残200株の平均原価1,500円が1,333.33円へ変わる。売却原価を戻しても、再適用で現在の平均原価を再計算すると後続取引まで巻き込む。価格・費用だけの訂正は元の取得原価差分を固定してキャッシュ差分だけ直すか、依存する後続取引を含め再計算する必要がある。

S03の注文中分割は現仕様で調整方針が未定義。倍増した保有だけでなく、注文数量・指値・逆指値・端株・約定報告の単位を合わせる必要がある。テストでは「注文がある間は分割を拒否して照合」を提案しており、現契約違反と断定しない。S15のEXTERNALがunconfirmedに出ない点も、現APIはSENT/EXPIREDの未確認だけを返すため追加契約が必要。運用では外部注文の照合状態を実行器へ別途渡すべき。

S12/S13は新しいresolve_pendingの検証漏れ。銘柄不一致でpendingになった行でもAPPLYで別銘柄へ計上でき、不明なactionもAPPLYとして動く。人間の操作でもcode/side/quantityの制約を解除しないこと。actionはAPPLY/DISCARDを列挙検証し、元CSVの訂正は別イベントで残す。

## 2. 全通知横断の重複照合

S06は同一注文・同数量・同価格でも時刻が異なる二つの部分約定を正しく計上した。S05は別銘柄の同キーがskippedになる。broker_order_idに全銘柄横断の一意性保証がない以上、銘柄・方向・口座・市場等を先に照合し、不一致は少なくともpendingにする必要がある。実CSV未確認のまま注文IDの一意性を仮定しない。

S07の時刻なし部分約定は現入力契約のaware datetimeを満たさないため、pending必須というテスト前提は拡張提案。ただし実装はNoneを受けて既存約定との重複を確定してしまう。対応するなら時刻精度・約定IDを追加し、対応しないなら入力拒否と監査記録を行う。

実CSVの列、約定ID、注文番号の採番範囲、日次集計行の扱いは今回も未検証。新しい実口座データやネットワークは使用していない。

## 3. replay・replay_known・監査

S08のreplay_known(seq)は後着訂正があっても以前の現金900,000円を再現し、現在現金901,000円と区別できた。一方S09は約定報告より後の時刻で通知を作成した場合、replay(at)が通知を除外して約定だけを再生し「通知がありません」で落ちる。現在のreportはこの到着順を受け付けているため、受け付けた履歴を業務時刻で再現できない反例である。元イベントの存在条件と業務時刻の有効範囲を分ける必要がある。

監査S10ではAPPLIED/DUPLICATE/IGNOREDとpayload_hashが残り、残高の重複変更もなかった。ただしS11の空ID拒否は監査0行。全受信試行という説明と一致しない。S16では監査表へのINSERTを失敗させるSQLiteトリガーを一時DBに設けると、reportが例外になるのに約定現金900,000円だけ確定していた。残高イベントのCOMMIT後に監査を別書込しているためで、APPLIED監査は残高と同一トランザクションにするべき。

追加のコード上の懸念：CSVの監査outcomeはskippedからSKIPPEDを作るため、説明のDUPLICATEと一致しない。同一IDの改変はpayload_hashを残すもののID_PAYLOAD_CONFLICTを分類しない。pending解決自体の監査主体・理由も不足。これらは今回の16件とは別のコードレビュー所見であり、専用テストで確認済みとはしない。

複数ハンドルのseq再読込は前回の順次競合を解消したが、状態の読取とMAX(seq)取得の間、COMMITとMAX(seq)取得の間に別書込が入る競合余地がある。更新と監査の全経路を単一書込主体へ集約する前提を維持する。実プロセスの競合ストレス試験は未実施。

## 4. reason_codesの粒度

コード追加はよいが、現実装は日本語文面の部分一致で後付けしている。文面修正でコードまで変わり、S14ではINVALIDがREVIEW_NOT_APPROVEDへ分類される。これは現コード定義を超える表示改善の提案であり、採否ゲート自体は拒否できている。

判定箇所で理由コードと表示パラメータを同時生成する案を推奨。REVIEW_INCOMPLETE（欠損・期限）、REVIEW_INVALID（形式不正・重複審査者）、REVIEW_NOT_APPROVED（正常なREJECT/ABSTAIN）を区別する。規制のUNKNOWNも「規制対象」と断言せず情報不足コードに分ける。日次実行器はINVALIDと受信期限を自分でも判定し、審査未完了をサインなしに変えない。

## 5. 順序3に必要なAPI

今回のAPI追加で、時刻付きcreate_notice、売却予約を含むview、営業日引数、seq、policy照合が使用可能になった。runner.pyはこれらを使って模擬専用台帳に対し、最新view→evaluate→create_notice→APPROVED→ローカルoutboxの順で直列処理する。pending_rowsもNEW停止条件へ加えた。

まだ不足するのは、台帳とoutboxを跨ぐ原子性、外部注文を含む照合状態、通知のProposal内容を読む公開API、既存INTENTを安全に復旧する公開操作、記録順と業務時刻を併用する再計算API、資産評価の統一スケール。runnerはこれらを推測で埋めず、途中に台帳だけ残った場合は予約を保持してSYSTEM_ERRORにする。自動復旧の完成や本番運用可とはしていない。
