**段2 はキー集合に依らず一意に決まる。**`history.mode` を `evidence_history_fixture_v2` にしたうえで、余分キーを足す・`decision_at` を落とす・`entries` を落とす・何もしないの 4 通りを試し、すべて `HISTORY_MODE_MISMATCH` 単独、4 件数 0、`selection_sha256=null` になった。依存 API がそれらを `INVALID_BUNDLE`（構造）と分類することは変わらないが、段2 が依存 API を呼ばないと明記されたため、両者が分かれることは仕様であって曖昧さではない。逆に `mode` キー欠落・非 dict・正しい mode ＋余分キーは、いずれも段3 の `INVALID_BUNDLE` 単独になった。第5回 R5-01 で指摘した二読は解消している。

**mode 以外の版差・封筒差は 9 種を増やさない。**`history.source_origin="live"`（依存 API は `INVALID_ORIGIN`）、`input.mode="strict_input_v2"`、`input.source_origin="live"` はいずれも段3 の `INVALID_BUNDLE` 単独、結合 mode の版差は段1 の `INVALID_BUNDLE` 単独になった。5 通りの版差・封筒差について、返る理由コードが閉じた 9 種の部分集合に収まることも試験で固定した。

**corrected は選択のある必須 subject に限られる。**`events/0001` の初版と訂正版がどちらも `as_of` より後にしか無い束では `corrected_after_as_of_count=0`、`reason_codes=['HISTORY_SELECTION_MISSING']` になった。選択のある `lots/0001` が後日訂正された束では、成功しつつ `corrected=1`。そして `events/0001` を履歴から落とし、`lots/0001` を後日訂正した束では、`HISTORY_SELECTION_MISSING` と `corrected=1` が同時に立ち、`matched=1` を返した。依頼が名指しした「併存」は起こり得るし、起きてよい。同じ revision の再取得を訂正に数えないことも併せて確認した。

**時点不一致では部品を呼ばない。**参照実装に `strict_validity` の呼出回数カウンタを入れ、`decision_at` を 1 分ずらした束で呼出 0 回・`DECISION_TIME_MISMATCH` 単独・`matched=0`・`digest=null` を実測した。`validity_documents` を空リストにした束でも、時点不一致なら呼出 0 回で `DECISION_TIME_MISMATCH` 単独、時点一致なら 1 回呼んで `VALIDITY_NOT_SATISFIED`（R4-04 の写像）になる。時点不一致でも `required` / `extra` / `corrected` の 3 件数は返り、後日訂正がある束では `corrected=1` が返った。

実測: 読めない。サイズ境界と出力規約は書かれているが、`link`／reparse point の拒否、読取中の差し替え検出、重複キー・非有限値の拒否といった既存の保護に触れていない。内側 3CLI はいずれも共用の読取器を使い、サイズ比較も `>` で実装されている。独立に書くと `>=` になったり保護が落ちたりし得る。

重要度: 低（安全側の既定に落ちる可能性が高いが、境界の 1 バイトが実装差になる）。
